# Safety Monitor

Локальная настольная программа для рабочих зон и видеонаблюдения.
Строгий классический интерфейс: меню, дерево зон слева, обзор камер,
таблица подключений и отдельные окна настроек.

Приложение хранит аккаунты, карточки рабочих, доступ к рабочим зонам и журнал
в PostgreSQL. Поддерживаются RF-DETR, проверка нескольких видов СИЗ
и инструменты обучения из GitHub.
Видео поступает только из добавленных источников. По умолчанию используется
локальный `best.pt` (YOLO: человек, каска, отсутствие каски). У новых камер
контроль **Каска** включён; его можно отключить в настройках камеры.
Камеры получают постоянный четырёхзначный ID. Он отображается в таблице,
на плитке наблюдения и в свойствах камеры; переименование его не меняет.

## Запуск

Рекомендуется Python 3.12 с Tkinter. Для базы требуется Docker Desktop
с Linux-контейнерами либо доступный PostgreSQL с параметрами из `.env`.

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1 setup
# Только если .env ещё нет:
Copy-Item .env.example .env
# В .env задайте POSTGRES_PASSWORD и SAFETY_MONITOR_DB_PASSWORD.
docker compose up -d --wait db
.\run.cmd
```

`run.ps1` выбирает работающее окружение `.venv-local`, затем `.venv`.
Если оба отсутствуют или ссылаются на удалённый Python, `setup` создаёт `.venv-local`
через Python 3.12. При активированном окружении работает `python main.py`.
Существующий `.env` повторно копировать не нужно. Запуск приложения не запускает
Docker автоматически: база должна быть доступна перед входом.

PostgreSQL 18 доступен на `127.0.0.1:5432`; порт можно изменить через
`SAFETY_MONITOR_DB_PORT` в `.env`. Контейнер — `safety-monitor-postgres`,
постоянный том — `safety_monitor_postgres_data`. Данные сохраняются после
`docker compose down`; удаление тома удалит базу. Приложение подключается
отдельным пользователем БД `safety_monitor`, а не суперпользователем `postgres`.
Путь тома для версии 18: `/var/lib/postgresql`, согласно
[документации образа PostgreSQL](https://hub.docker.com/_/postgres).

Таблицы создаются автоматически при первом входе. Новая база объектов пуста;
зоны, камеры, рабочих и дополнительные аккаунты инспекторов добавляет администратор.
Карточки, фотографии, назначения, настройки и события сохраняются в PostgreSQL.
Если PostgreSQL выключен, форма входа сообщает об ошибке и позволяет повторить вход.

## Аккаунты и права

| Логин | Начальный пароль | Роль |
| --- | --- | --- |
| `admin` | `12345` | Администратор |
| `daniyal` | `12345` | Инспектор |

Эти аккаунты создаются при первоначальной настройке; существующие пароли не меняются.
Администратор добавляет других инспекторов во вкладке **Инспекторы**:
**Добавить инспектора…**, имя и фамилия, логин, пароль. Вкладка также доступна
через **Вид → Инспекторы**. Новый инспектор получает доступ к зонам только после назначения.
Кнопка **Изменить…** открывает имя, логин и новый пароль; пустой пароль сохраняет прежний.
**Удалить…** закрывает вход и убирает назначения инспектора из всех зон.
Рабочие, камеры и история журнала сохраняются.

| Возможность | Администратор | Инспектор |
| --- | --- | --- |
| Личные настройки приложения | Для своего аккаунта | Для своего аккаунта |
| Камеры, рабочие и журнал | Все зоны | Только назначенные зоны |
| Подключить/отключить просмотр, сохранить кадр, экспортировать журнал | Да | В доступных зонах |
| Комментарии и отметка «Просмотрено» | Да | В доступных зонах |
| Создание и изменение зон, камер, модулей СИЗ и назначений | Да | Нет |
| Общая модель распознавания | Да | Нет |
| Создание, изменение и удаление рабочих и инспекторов | Да | Нет |
| Удаление событий журнала | Да | Нет |

**Настройки → Настройки приложения** доступны обеим ролям. Тема, количество
камер в строке, автоподключение и интервал повторного подключения сохраняются
отдельно для каждого аккаунта. Изменение темы инспектором не меняет настройки
администратора или другого инспектора. Общую модель распознавания меняет администратор.

**Файл → Выйти из аккаунта** закрывает просмотр и возвращает форму входа.
Пароли хранятся как PBKDF2-SHA256 с индивидуальной солью и 600 000 итераций.

## Рабочие и доступ к рабочей зоне

Работа в приложении — это рабочая зона с камерами, инспекторами и рабочими.
Карточка рабочего содержит имя, фамилию, необязательное фото и автоматически
выданный ID от `1000` до `9999`. ID остаётся у карточки при изменении имени;
после удаления он не выдаётся другому рабочему. Рабочему не нужны логин и пароль.
Фотография служит для просмотра карточки: приложение не распознаёт личность
рабочего по видео и не связывает обнаружения СИЗ с его ID автоматически.

Порядок настройки администратором:

1. Во вкладке **Инспекторы** создайте нужные аккаунты для входа.
2. Во вкладке **Рабочие** нажмите **Добавить рабочего…**, укажите имя и фамилию.
   При необходимости выберите фото JPEG, PNG или WebP до 5 МБ.
3. В панели **Рабочие зоны** нажмите **Создать…**. Введите название, отметьте
   одного или нескольких инспекторов в списке **Инспекторы с доступом**
   и выберите карточки в списке **Рабочие в зоне**.
4. Добавьте камеры. Название и состав существующей зоны меняются кнопкой
   **Изменить…** или через **Файл → Участники и настройки рабочей зоны…**.

Карточку рабочего можно изменить или удалить во вкладке **Рабочие**.
Удаление требует подтверждения и убирает рабочего из всех назначений;
зоны, камеры и сохранённые события остаются. Новая карточка первоначально
не назначена ни в одну зону — включите её в состав нужной зоны.
Один инспектор или рабочий может входить в несколько зон.

Зона без назначенных инспекторов видна только администратору. Инспектор видит
дерево своих зон, их камеры, состав рабочих и события журнала. При открытии
вкладки **Рабочие** показывается состав выбранной зоны; кнопка
**Все доступные зоны** переключает на общий доступный список.

Права проверяются при каждом запросе к данным, включая открытие фотографии,
кадра, запись события, экспорт и изменение комментария. После снятия назначения
новые запросы инспектора к этой зоне запрещены сразу. Открытое приложение
проверяет назначения каждые 3 секунды и убирает отозванные зоны, прекращает
просмотр их камер и очищает ранее открытые карточки и кадры.

Удаление зоны удаляет её камеры и назначения. История событий и кадры сохраняются
и после удаления зоны доступны администратору.

## Журнал и библиотека кадров

Откройте вкладку **Журнал**, кнопку **Журнал / кадры** или **Вид → Журнал и библиотека кадров**.
Журнал и библиотека встроены в главное окно рядом с вкладками
**Наблюдение** и **Камеры**; оформление использует общие цвета,
шрифты, кнопки и таблицы.
Во вкладке **Журнал** доступны поиск по объекту/камере, фильтр статуса
и страницы по 100 событий. Двойной щелчок открывает кадр во вкладке
**Библиотека кадров**. Можно сохранить JPEG и отметить событие просмотренным
с комментарием; сохраняются имя проверившего и время проверки.
В таблице отдельно показаны **Вид нарушения** и **Количество**. YOLO `best.pt`
создаёт события **Отсутствие каски**; RF-DETR может создавать события об отсутствии
каски, жилета, очков и перчаток, в зависимости от классов выбранной модели
и включённых модулей камеры. Несколько видов сохраняются отдельными записями.

**Экспорт CSV** выгружает все записи по текущему поиску и фильтру статуса,
включая другие страницы. Файл открывается в Excel, содержит вид нарушения,
статус, проверившего и комментарий. Кадр сохраняется отдельно в JPEG.
**Сохранить комментарий** обновляет текст, не меняя статус проверки.
Администратор может выделить одну или несколько записей и нажать
**Удалить выбранные**; после подтверждения удаляются записи вместе с кадрами.
Инспектор не может удалять события и работает только с журналом назначенных ему зон.
Это ограничение действует также на экспорт CSV и открытие кадра по ID события.

Список, кадры, сохранение и экспорт загружаются независимо: ожидание кадра
не блокирует переходы страниц и удаление. Поиск применяется при вводе, фильтр
статуса — при выборе. Страница меняется после успешного ответа БД; если удалить
последнюю запись на странице, журнал возвращается к предыдущей. Черновик
комментария сохраняется при переключении записей и обновлении списка.
При возвращении на вкладку журнал обновляется, сохраняя текущую страницу.

При подтверждённом результате анализа автоматически сохраняются время записи, объект,
камера, число обнаружений и обработанный кадр. Не более одного события
одного вида с камеры за 30 секунд, включая повторные запуски и другие экземпляры программы.
Это выборка положительных детекций, не подсчёт уникальных людей или нарушений.
Кадры хранятся в PostgreSQL вместе с событиями и остаются после удаления объекта.
Запись идёт в ограниченной фоновой очереди; ошибка базы или переполнение
показываются в нижней строке окна наблюдения. При выходе из аккаунта форма
входа открывается сразу; очередь уже обнаруженных событий дописывается в фоне
с отдельным правом только на запись событий. Сессия пользователя закрывается
сразу. Фоновая запись также проверяет актуальный доступ к зоне и не обходит
снятое назначение. При закрытии программы окно исчезает сразу, а процесс завершает запись
очереди в фоне. Ошибка базы может привести к потере не записанных кадров.
Наблюдение работает только для камер
открытой страницы, поэтому события закрытых страниц не собираются.

## Подключение IP-камеры

1. Слева нажмите **Создать…**, задайте название рабочей зоны и её участников.
2. Нажмите **Добавить камеру…**.
3. Укажите название и выберите **IP-камера (RTSP)**.
4. Введите полный RTSP-адрес потока вашей камеры, например по шаблону:

   ```text
   rtsp://USER:PASSWORD@192.168.1.50:554/STREAM_PATH
   ```

5. Выберите транспорт **TCP** или **UDP** и сохраните камеру.

`USER`, `PASSWORD`, адрес и `STREAM_PATH` заменяются параметрами вашей камеры.
Точный путь берётся из документации или веб-интерфейса производителя.
Камера должна быть доступна с компьютера, а RTSP — включён в её настройках.
Специальные символы в логине/пароле требуется кодировать для URL.

По умолчанию камеры подключаются при открытии зоны. Это поведение можно
отключить в **Настройки → Настройки приложения**. Кнопки **Подключить** и
**Отключить** работают с выбранной камерой; если выбрана сама рабочая зона,
они применяются к камерам текущей страницы.

При недоступности RTSP показывается состояние ошибки и выполняется повторное
подключение (по умолчанию через 5 секунд). Демонстрационное изображение не подставляется.
Настроены таймауты открытия 5 секунд и чтения 3 секунды для FFmpeg.
Параметры таймаутов передаются при открытии захвата, как предусмотрено
[API OpenCV](https://docs.opencv.org/4.x/d4/d15/group__videoio__flags__base.html).

Также поддерживаются USB-камеры по индексу устройства и локальные видеофайлы.
Видеофайл повторяется после окончания, изображение сохраняет исходные пропорции.

## Рабочие зоны и камеры

- Создание, открытие, изменение названия и состава, удаление зон через левую панель и меню **Файл**.
- Дерево камер внутри каждой зоны и отдельная вкладка **Камеры** с таблицей.
- Добавление, изменение подключения и удаление камер через панель инструментов
  или меню **Камеры**. Двойной щелчок по строке таблицы открывает свойства.
- Контекстное меню таблицы для подключения и настройки выбранной камеры.
- Обзор в 1, 2 или 3 колонки; на узком окне количество колонок уменьшается.
- До 9 камер на странице. Потоки других страниц закрываются; переходы доступны
  кнопками **Назад / Далее**. Выбор камеры в дереве/таблице открывает её страницу.
- Личные настройки обеих ролей: светлая, тёмная и системная темы, вид камер и параметры подключения.
- Горячие клавиши: **Ctrl+N** — создать зону, **Ctrl+O** — открыть зону.

## Модели и модули СИЗ

Администратор выбирает модель в **Настройки → Настройки приложения**.
Выбор сохраняется в PostgreSQL для последующих запусков. При смене модели
сбрасываются результаты и история отслеживания предыдущей модели.

| Модель | Файлы | Контроль |
| --- | --- | --- |
| Локальная YOLO | `best.pt` в корне | Каска |
| RF-DETR model-v1 | `weights/model-v1.pt` + `model-v1.labels.json` | Каска, жилет, очки, перчатки |
| RF-DETR model-v2 | `weights/model-v2.pt` + `model-v2.labels.json` | Каска, жилет, очки, перчатки |
| RF-DETR weights | `weights/weights.pt` + `weights.labels.json` | По карте классов весов |

**В GitHub находятся карты классов, но сами RF-DETR веса `.pt` в Git не добавлены.**
При слиянии существующий локальный `best.pt` сохранён. Чтобы включить RF-DETR,
нужно скопировать соответствующие веса вместе с их картой классов и установить
дополнительные зависимости:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1 setup-rfdetr
```

Можно выбрать другую локальную пару RF-DETR через **Выбрать файл…** в настройках.
Карта `.labels.json` привязана к SHA-256 конкретного файла весов. Порядок классов
не угадывается: неполная карта отключает регистрацию нарушений, несовпадение
хеша показывает ошибку. Для запуска YOLO дополнительные RF-DETR зависимости не нужны.

Выберите камеру и откройте **Модули СИЗ…**. Каска, жилет, очки и перчатки
настраиваются отдельно для каждой камеры. Обувь, респиратор и защита слуха
сохраняются в конфигурации, но эти модели их не поддерживают. При выбранном
`best.pt` доступен контроль каски; остальные возможности зависят от RF-DETR.

YOLO `best.pt` использует прямые детекции `No-Helmet` с порогом 0.4.
RF-DETR использует классы `NO …`, а также проверку отсутствия экипировки у
достаточно крупного, полностью видимого человека. Неоднозначное сопоставление
в толпе и обрезанные фигуры не дают основания для проверки по отсутствию.
Событие RF-DETR требует устойчивого наблюдения в течение 30 секунд на одной камере;
смена источника, настроек или модели сбрасывает накопленную историю.
События требуют проверки оператором. Отсутствие детекции нарушения не означает,
что экипировка присутствует у каждого человека. Учёт инцидентов выполняется
в пределах одной камеры; события разных камер не подавляются по похожей одежде.

Загрузка и вызовы модели выполняются в фоне и сериализованы для всех камер.
Новые кадры заменяют ожидающие, очередь не растёт; рамки выводятся на том кадре,
который обработала модель. Отправка на анализ — не более 5 кадров/с с камеры;
фактическая скорость зависит от компьютера. При отсутствии весов или зависимостей
видео продолжает работать, а статус камеры показывает причину недоступности анализа.

## Сохранение и закрытие

Рабочие зоны, адреса, модули, назначения и общая модель сохраняются в `application_config`
в PostgreSQL одной транзакцией. Личные настройки аккаунтов находятся в `user_preferences`,
карточки рабочих и фотографии — в `workers`. При ошибке изменения в памяти отменяются.
Защита по версии запрещает перезаписать конфигурацию, изменённую другим
администратором; для обновления нужно заново войти в аккаунт.
Сохранённый видеофайл, который был перемещён или удалён, не мешает запуску программы.

RTSP-адрес вместе с введёнными учётными данными хранится в базе.
В таблице источников логин, пароль и query-параметры скрыты.
`.env` с паролями БД исключён из Git. Локального хранилища объектов нет.

Каждый видеопоток читается отдельным фоновым потоком. Он же выполняет
`VideoCapture.release()` в `finally`; интерфейс обновляется через `after()`
в основном потоке. Отмена подключения очищает старое изображение, а закрытие
окна останавливает захваты и отменяет обновления интерфейса.
При зависании нативного USB-драйвера поток сможет освободить устройство
после возврата из вызова драйвера. Интерфейс не ждёт завершения этих вызовов
при выходе из аккаунта или закрытии окна.

Изменение зон, камер, модулей и настроек выполняется в фоне. Изменения
публикуются в интерфейсе только после успешной записи в PostgreSQL; во время
сохранения окно продолжает обрабатывать нажатия. Одновременно выполняется
одно сохранение конфигурации. Неизменившийся обработанный кадр повторно
не отрисовывается; скрытые видеоплитки не тратят время на отрисовку.

## Обновление существующей базы

При входе автоматически применяется миграция схемы до версии 3. Она добавляет
карточки рабочих, личные настройки, назначения и связь событий со стабильным ID зоны.
Существующие аккаунты, камеры и события сохраняются; прежние параметры просмотра
копируются в личные настройки уже созданных аккаунтов.

У существующих зон список инспекторов изначально пуст: после обновления они
доступны администратору, пока он не назначит инспекторов через **Изменить…**.
Старые события связываются с зоной по ID камеры или однозначно определяемому
названию зоны. История, которую нельзя связать с действующей зоной, остаётся
доступной администратору.

Резервная копия папки проекта не включает данные PostgreSQL из Docker-тома.
Для сохранения аккаунтов, карточек, фотографий и журнала нужна отдельная резервная
копия базы PostgreSQL. Миграция выполняется в транзакции и не заменяет такую копию.

## Проверки

```powershell
.\.venv-local\Scripts\python.exe -m unittest discover -s tests -v
# Проверки PostgreSQL в отдельных временных схемах:
$env:SAFETY_MONITOR_TEST_DB="1"
$env:OPENBLAS_NUM_THREADS="1"
.\.venv-local\Scripts\python.exe -m unittest discover -s tests -v
# Дополнительно проверить окна, персонал, назначения и отзыв доступа (нужен рабочий стол):
$env:SAFETY_MONITOR_TEST_UI="1"
.\.venv-local\Scripts\python.exe -m unittest discover -s tests -v
```

Проверки БД читают пароль `postgres` из `.env`, создают собственные тестовые
схемы и удаляют только их. Объекты и журнал основной схемы не меняются.
Проверки доступа охватывают личные настройки, несколько инспекторов с разными
зонами, карточки и фотографии рабочих, ограничения журнала и отзыв доступа
при открытом окне наблюдения.

Рабочее приложение не содержит демонстрационных камер, событий или подмены
БД. Интеграционные тесты создают данные в отдельных схемах, которые удаляются
после проверки; модульные тесты используют собственные изолированные данные.

## Обучение и проверка датасетов

Из GitHub сохранены `models.py` (подготовка датасета и обучение YOLO),
`train_weights.py` (RF-DETR), `prepare_ppe_review.py`, `autolabel_people.py`,
`autolabel_ppe.py`, `apply_visual_ppe_review.py` и их проверки.
Датасеты, веса и результаты обучения локальные; они не скачиваются при обычном
запуске программы и не входят в Git. Исторический `result.json` — результат
предыдущего эксперимента, а не оценка объединённой версии.

Подготовка Construction-PPE для YOLO:

```powershell
.\.venv-local\Scripts\python.exe -m pip install -r requirements-training.txt
powershell -ExecutionPolicy Bypass -File .\run.ps1 prepare
.\.venv-local\Scripts\python.exe models.py --profile cpu
```

Обучение RF-DETR требует исходной пары `weights/weights.pt` и `weights.labels.json`,
датасета COCO и NVIDIA CUDA с подходящей сборкой PyTorch. Обычный `setup` не
устанавливает отдельную CUDA-сборку принудительно. Сначала установите PyTorch
для своей видеокарты по официальной инструкции, затем зависимости обучения:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1 setup-training
powershell -ExecutionPolicy Bypass -File .\run.ps1 train --prepare-only --dataset data/ppe_full_annotation_review
powershell -ExecutionPolicy Bypass -File .\run.ps1 train --smoke --minutes 5
powershell -ExecutionPolicy Bypass -File .\run.ps1 train --minutes 90
```

`train90.cmd` запускает тот же 90-минутный профиль. Подготовка и финальное
сохранение могут занять дополнительное время. Новые веса и карта классов
попадают в `runs/rfdetr/<дата-время>-90min/`; рабочая модель автоматически
не заменяется. Режим `--deploy` доступен только для проверенного датасета
(`training_ready: true`) и положительной метрики validation.

Проверка готовых RF-DETR весов на своей фотографии без изменения базы:

```powershell
.\.venv-local\Scripts\python.exe -m tests.weights_smoke --image "C:\video\frame.jpg" --model weights/model-v2.pt
```

Аннотированное изображение и отчёт сохраняются в `.artifacts/weights-review`.
Проверка полного входа, прав и журнала в отдельной схеме PostgreSQL:

```powershell
.\.venv-local\Scripts\python.exe -m tests.gui_smoke
```
